## 1. 设计目标与范围

### 1.1 本期设计覆盖

| 范围 | 内容 |
|---|:--|
| 覆盖 | 任务框架、解析、存储、版本、AI 层、拆书流水线、编辑器并发、API、数据库、部署 |
| 不覆盖（后续迭代） | 多人协作编辑（OT/CRDT）、移动端适配、社区/素材共享、语音输入 |

### 1.2 关键设计原则

1. **AI 一律异步化、任务化**：任何 AI 调用都不得出现在用户请求的同步链路中。
2. **正文与元数据分离存储**，元数据小表快查，正文大字段独立存储。
3. **所有可重试操作幂等**：任务以 `task_id` 去重，AI 结果以 `(task_type, biz_id, prompt_hash)` 缓存。
4. **能降级就降级**：AI 服务挂了，解析、编辑、导出全部可用。

      └──────┬───────┘    └─────────────┘ └──────────┘   └──────────────┘

      ┌──────▼─────────────────────────────────────────┐

      │  路由 → 限流 → 熔断 → Provider(OpenAI/DeepSeek/ │
      │  通义/本地 vLLM) → 结果缓存 → 成本记账           │

**进程模型**：API 服务与 Worker 共用同一套代码，通过部署时开启不同 profile 分离：
- `api`：对外 HTTP（无并发任务消费）
- `worker`：消费任务队列（可通过 `--app.worker.count=N` 水平扩容）

初期单实例用 Spring `@Async` + DB 任务表即可；任务量上来后把"取任务"换成 RabbitMQ（接口已隔离，切换成本仅限任务存取适配器）。

## 3. 核心设计决策（ADR 摘要）

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| ADR-1 | 拆书原书与用户作品是否同表 | **分表**（`source_book` vs `novel`） | 数据生命周期、权限、版权处理完全不同 |
| ADR-2 | 章节正文存哪 | **MySQL 大字段独立表**（`chapter_content`），>2MB 的卷导出走 MinIO | 事务一致性、备份简单；MinIO 只存原文和导出产物 |
| ADR-3 | 版本历史存法 | **最近 20 版全量 + gzip 压缩**，不做 diff | 百万字文本 gzip 压缩率约 70%，diff 实现/回滚复杂度高，收益小 |
| ADR-4 | AI 调用方式 | **全部任务化 + Provider 抽象 + 双 provider 降级** | 避免阻塞请求线程；供应商可切换 |
| ADR-5 | 编辑器并发控制 | **版本号乐观锁（CAS）** | 单人创作场景为主，无需锁服务；冲突时引导用户合并 |
| ADR-6 | 进度推送 | **SSE**（Server-Sent Events） | 单向推送足够，比 WebSocket 简单，比轮询省资源 |
| ADR-7 | 章节自动拆分 | **正则规则引擎**，预置中文/英文模板 + 用户自定义 | 纯规则零成本，AI 拆分留作兜底选项 |

## 4. 模块详细设计

### 4.1 异步任务框架

#### 4.1.1 任务模型

所有长耗时操作统一抽象为 `Task`：

```java
public enum TaskType {
    BOOK_PARSE,          // 拆书：解析+分章
    BOOK_ANALYZE,        // 拆书：AI 分析（摘要/情绪/人物…）
    REPORT_GENERATE,     // 拆书：生成报告
    AI_CONTINUE_WRITE,   // AI 续写
    AI_POLISH,           // AI 润色/改写
    EXPORT,              // 导出 TXT/DOCX/EPUB/PDF
    CONSISTENCY_CHECK    // 一致性检查
}

public enum TaskStatus {
    PENDING,     // 已入队
    RUNNING,     // 执行中
    SUCCESS,     // 成功
    FAILED,      // 失败（可重试）
    CANCELED,    // 用户取消
    DEAD         // 重试耗尽，进入死信
}
```

#### 4.1.2 状态机

```
            ┌─────────┐  worker抢占   ┌──────────┐
  submit ──▶│ PENDING │──────────────▶│ RUNNING  │──┬──▶ SUCCESS
            └─────────┘               └────┬─────┘  │
                 ▲   │超时未领取(10min)      │         ├──▶ FAILED ──重试≤3次──▶ RUNNING
                 │   └──────────────────────┤         │                          （退避：1m/5m/15m）
                 │   用户取消                ├──▶ CANCELED
                 │                          └──▶ FAILED（重试耗尽）──▶ DEAD
```

规则：
- **幂等抢占**：`UPDATE task SET status='RUNNING', worker_id=?, started_at=NOW() WHERE id=? AND status='PENDING'`（CAS），多 worker 安全。
- **心跳与续命**：RUNNING 任务每 30s 更新 `heartbeat_at`；超过 90s 无心跳视为僵死，重置为 PENDING 重新调度。
- **用户级互斥**：同一 `biz_id`（如同一 source_book）存在 RUNNING 任务时，新任务直接拒绝并返回已有任务 ID。
- **取消**：仅 PENDING 可无损取消；RUNNING 通过 Redis 发布 `cancel:{taskId}`，worker 在章节/批次粒度检查。
- **进度**：`progress`（0-100）+ `progress_msg`（当前在做第几章），写入 DB 并同步 publish 到 Redis channel。

#### 4.1.3 进度推送（SSE）

```
GET /api/tasks/{id}/events        ← SSE 长连接
事件流：
  event: progress  data: {"progress": 42, "msg": "分析第 210/500 章"}
  event: done      data: {"status":"SUCCESS","resultRef":"..."}
  event: error     data: {"code":"AI_RATE_LIMIT","msg":"..."}
```

前端断线重连：携带 `Last-Event-ID`，服务端补发最新一次进度快照。

#### 4.1.4 任务表关键字段

```
task
  id              bigint PK
  type            varchar(32)
  biz_id          varchar(64)     -- 关联对象，如 source_book:123 / chapter:456
  user_id         bigint
  status          varchar(16)
  progress        tinyint
  progress_msg    varchar(255)
  param_json      json            -- 任务参数（幂等键也放这）
  result_json     json            -- 概要结果（详情落业务表）
  error_code      varchar(32)
  error_msg       text
  idem_key        varchar(64) UK  -- 幂等键：type+biz_id+paramHash，防重复提交
  retry_count     int
  next_retry_at   datetime
  worker_id       varchar(64)
  heartbeat_at    datetime
  created_at / updated_at / finished_at
```

### 4.2 文件上传与章节解析

#### 4.2.1 上传流程

```
前端            API                     MinIO              DB
 │  ① POST /api/sources (multipart)  │                   │
 │──────────────────────────────────▶│                   │
 │                                   │ ② 流式写入 tmp/   │
 │                                   │──────────────────▶│
 │                                   │ ③ 记录 source_book │
 │                                   │    status=UPLOADED │
 │  ④ 返回 sourceId ────────────────▶│                   │
 │  ⑤ POST /api/sources/{id}/parse ─▶│ ⑥ 创建 BOOK_PARSE  │
 │                                   │    任务(PENDING)   │
 │  ⑦ SSE 订阅任务进度 ──────────────▶│                   │
 │  ⑧ 100% 后 GET 章节列表 ──────────▶│                   │
```

- 上传上限 50MB，校验扩展名 + MIME + 魔数（防止改后缀），`.txt` 强制按 UTF-8/GBK 探测解码（juniversalchardet）。
- 文件先写 MinIO `tmp/` 目录，解析成功后才转正到 `books/`；失败任务 7 天后由清理任务删除。
- **大文件流式解析**：TXT 按 8MB 块读取，边读边用正则匹配章首；DOCX 用流式 SAX 读取（避免 DOM 全量加载）；EPUB 用 zip 流逐个 entry 处理。

#### 4.2.2 章节识别规则引擎

```java
public interface ChapterSplitRule {
    String name();
    Pattern headPattern();       // 匹配章节标题行
    boolean isVolumeHead(String line);  // 分卷判断
}

// 预置规则
rule-cn-1: ^第[0-9零一二三四五六七八九十百千两]+[章回节卷部].{0,40}$
rule-cn-2: ^Chapter\s+\d+.*$          (i)
rule-cn-3: ^\d+[\.、]\s*\S.{0,40}$    // 1. 标题 / 1、标题
rule-custom: 用户输入 Java regex（带安全校验，禁止灾难性回溯：长度限制+ReDoS 检测）
```

执行策略：按规则优先级逐行扫描，命中行作为新章节起点；一章内命中分卷行则新建 volume。**识别结果预览**：解析完成后先返回"识别出 512 章 / 置信度"，用户可人工修正标题或合并错误分章（前端提供章节列表编辑），确认后才进入分析。

#### 4.2.3 分章入库

- 单章字数若 > 2 万字（部分作者不分章），按 3000 字硬切并标记 `is_auto_split=1`。
- 入库批处理：每 50 章一个事务，`INSERT ... ON DUPLICATE KEY UPDATE`（同一 source 重复解析时按 `source_chapter_no` 幂等覆盖）。
- 全文检索：不入库阶段建，避免拖慢解析；需要时引入 Elasticsearch（预留 `chapter_content` 同步 Canal → ES，本期用 MySQL `LIKE` + 章节内搜索即可）。

### 4.3 章节正文存储与版本历史

#### 4.3.1 存储结构

```
chapter                -- 元数据小表（列表页/目录树查询走这里）
  id, novel_id, volume_id, title, sort, word_count,
  status(DRAFT/FINISHED), version(当前版本号), updated_at
  索引：uk(novel_id, sort)

chapter_content        -- 正文大字段表
  id, chapter_id FK, content MEDIUMTEXT, content_gzip blob(冗余可选),
  word_count, editor_format(RICH/MD), created_at
  索引：uk(chapter_id)  -- 一对一当前版本

chapter_version        -- 历史版本
  id, chapter_id, version, content MEDIUMTEXT, word_count,
  save_type(AUTO/MANUAL/AI_REPLACE/BRANCH), created_by, created_at
  索引：idx(chapter_id, version desc)
  策略：每章最多保留 20 版，超出删除最旧；gzip 压缩存储（应用层）
```

**为什么版本全量而非 diff**：百万字 ≈ 2MB，gzip 后约 0.6MB，20 版 ≈ 12MB/章，1000 章 ≈ 12GB——接受范围内（可配保留版数与过期清理）。diff 方案实现成本高（分段对齐、跨版本组合回滚），单人创作场景收益低。此为 ADR-3。

#### 4.3.2 版本产生时机

| 时机 | 是否产生新版本 |
|---|---|
| 自动保存（防抖 5s 触发） | ✗ 直接覆盖 chapter_content |
| 每隔 10 分钟定时 | ✓ 记为 AUTO 版（版本表） |
| 手动保存 / 手动"存档" | ✓ MANUAL 版 |
| AI 续写采纳 / 替换全文 | ✓ AI_REPLACE 版（便于"丢弃 AI 结果"一键回滚） |
| 每天首次打开章节 | ✓ 记当日基线版 |

#### 4.3.3 回滚

`POST /api/chapters/{id}/rollback?toVersion=N`：将 N 版内容复制为当前内容（chapter_content），version+1，并记录回滚日志（auditable）。

### 4.4 AI 服务抽象层（AiGateway）

#### 4.4.1 接口定义

```java
public interface AiProvider {
    String name();                                  // "openai" / "deepseek" / "qwen" / "local-vllm"
    ChatResponse chat(ChatRequest request);         // 非流式
    Flux<ChatChunk> chatStream(ChatRequest request); // 流式(SSE回前端)
    int maxContextTokens();
    boolean supports(Ability ability);              // STREAM/JSON_MODE/FUNCTION_CALL/EMBEDDING
}

public class ChatRequest {
    String model;
    List<Message> messages;        // system/user/assistant
    Double temperature;
    Integer maxTokens;
    Boolean jsonMode;              // 强制 JSON 输出
    Integer timeoutSeconds;        // 默认 120
}

public class ChatResponse {
    String content;
    Usage usage;                   // promptTokens/completionTokens
    String model;
    Long latencyMs;
    String provider;
}
```

#### 4.4.2 网关职责（调用链）

```
业务代码 ─▶ AiGateway.chat(req)
   ① 限流：用户级令牌桶（Redis, 默认 10 req/min；任务通道独立额度 60 req/min）
   ② 成本控制：单用户日额度（配置项，默认 ¥2/天），超限抛 AiQuotaExceeded
   ③ 缓存：key = sha256(provider|model|prompt) → 命中直接返回
   ④ 路由：按任务类型配置 provider 优先级，如 analyze→[deepseek, qwen]
   ⑤ 熔断：provider 连续失败 5 次/30s → 熔断 60s → 半试探恢复
   ⑥ 降级：主 provider 失败按优先级切换；全挂 → 任务 FAILED(可重试)，编辑器等非核心功能不受影响
   ⑦ 记账：异步写 ai_log（tokens、折算成本、任务ID、promptHash）
```

#### 4.4.3 Prompt 管理

- 所有 Prompt 模板存 `prompt_template` 表（`code, version, content, params_schema, enabled`），**不硬编码在代码里**；
- 模板含变量占位 `{{变量}}`，渲染时校验参数 schema；
- 结构化输出（摘要/情绪打分）统一 `jsonMode=true` + 服务端 JSON Schema 校验，**解析失败自动重试 1 次**（重试时追加"上次输出非法 JSON"提示），仍失败则该章标记 `analyze_status=FAILED` 不阻塞整体任务。

#### 4.4.4 降级预案

| 场景 | 行为 |
|---|---|
| AI 全部不可用 | 拆书退化为纯统计（字数/章节/人物频次规则提取），报告页明确标注"AI 分析不可用"；编辑器所有 AI 按钮置灰并提示 |
| 速率限制 | 任务侧指数退避（1m→2m→4m…上限 30m），不直接判失败 |

### 4.5 拆书分析流水线

#### 4.5.1 任务编排

一次"开始分析" = 一个 `BOOK_ANALYZE` 任务，内部按阶段执行，**每章每类分析独立成 step，可断点续跑**：

```
阶段A 章节摘要+情绪打分（逐章 AI，可并发 5 路）
阶段B 人物抽取（逐章 NER：先用 jieba+规则词典零成本初筛，
      仅对"疑似新人物/低置信"章节调 AI 确认 —— 成本约降为全量 AI 的 15%）
阶段C 共现统计 + 关系图构建（纯计算）
阶段D 关键词/节奏统计（纯计算：TF-IDF、对话占比正则）
阶段E 汇总报告（一次 AI 调用，输入为 A~D 的聚合结果）
```

- **断点续跑**：每章每阶段结果落 `analysis_chapter`，重跑时跳过已完成 step（以 `prompt_template.version` 为缓存键，模板升级后自动失效重算）。
- **抽样模式**（成本控制开关）：`sample_mode=true` 时摘要仅对每 3 章抽 1 章执行，情绪曲线用插值补齐，UI 标注"抽样分析"。
- **并发**：任务内章节级并发 5（可配），受全局 AI 限流约束。

#### 4.5.2 章节分析结果结构（analysis_chapter）

```json
{
  "chapter_id": 210,
  "summary": "主角被退婚后觉醒系统，当众打脸未婚妻家族。",
  "tension": 8,                // 冲突强度 1-10（AI 打分）
  "emotion": 6,                // 情绪值 -10 ~ +10
  "tags": ["高潮", "反转"],     // 高潮/悬念/反转/日常/过渡
  "dialogue_ratio": 0.42,      // 对话占比
  "characters": ["林凡", "苏婉儿"],
  "keywords": ["退婚", "系统", "打脸"],
  "status": "DONE"
}
```

**情节曲线 = tension 折线 + emotion 面积图**（ECharts 双轴）；爽点标记 = tags 含"高潮/反转"的章节打点。**注意**：tension 定义为"Prompt 中给出 6 个示例章节的锚定打分"（few-shot 锚定），避免模型打分漂移——这是情绪值可用的关键。

#### 4.5.3 人物关系图

- **边权**：人物 i,j 在同章共现次数；**出现 ≥3 次才建边**（降噪）。
- **关系类型**：共现不推断关系。采用半自动：AI 对 Top 50 高频共现对各做一次关系推断（输入：共现章节号列表 + 各章摘要，输出如 `{"a":"林凡","b":"苏婉儿","rel":"未婚妻→仇敌","confidence":0.8}`），confidence < 0.6 显示"关系待确认"。用户可手工编辑关系，编辑结果持久化并优先于 AI 结果。
- 渲染：ECharts Graph，力导向布局，节点大小 = 出场频次。

#### 4.5.4 报告

- `analysis_report` 存聚合 JSON（曲线数据、Top 人物、节奏统计、AI 总结）；
- 导出 PDF：后端用 Freemarker/HTML 模板渲染 → headless Chrome / openhtmltopdf 转 PDF（中文排版用模板内置字体）；Markdown 直接序列化。

### 4.6 编辑器与自动保存（并发控制）

#### 4.6.1 保存链路

```
ProseMirror onUpdate
   │ 防抖 5s ──▶ 本地 IndexedDB 草稿(双保险)
   │ 定时 15s ──▶ POST /api/chapters/{id}/content
                    body: {content, baseVersion: 12, format}
                    服务端: UPDATE ... SET content=?, version=version+1
                            WHERE id=? AND version=12   ← CAS
   ├─ 影响行数=1 → 200 {version:13}
   ├─ 影响行数=0 → 409 CONFLICT {serverVersion:14, serverContent?}
                    前端弹出三方对比：保留我的 / 用服务器 / 手动合并
```

- **乐观锁而非锁服务**：单人创作为主，多端（PC 两个标签页）冲突概率低，CAS 足够且零额外组件。
- 保存请求带 `Idempotency-Key: chapterId+baseVersion`，网络重试不产生重复版本。

#### 4.6.2 断网草稿策略

- 编辑即写 IndexedDB（key = chapterId，含 updatedAt）。
- 恢复逻辑：
  1. 打开章节 → 比较 `localDraft.updatedAt` 与 `server.updatedAt`；
  2. 本地更新 → 弹窗"发现本地草稿（10-04 16:20），是否恢复？"；
  3. 用户确认后才覆盖编辑器，永不静默覆盖服务端内容（ADR：服务端为准，本地草稿仅提示）。

#### 4.6.3 AI 续写/润色交互

- 续写：编辑器内联生成（流式 SSE 逐字输出），生成中可"停止"；采纳 = 插入光标处并产生 AI_REPLACE 版本，"丢弃" = 不产生版本。
- 续写输入组装：`最近 3000 字 + 本章大纲 + 相关人物卡(按最近出现角色取 top5) + 用户选择走向`；超长时按 token 预算截断（优先保留最近上下文 > 大纲 > 设定）。

---

### 4.7 拆书 ↔ 创作联动

数据上拆书结果挂在 `source_book` 下，创作挂在 `novel` 下，联动通过"参考引用"实现而非数据合并：

```
联动功能                    实现方式
──────────────────────────────────────────────────────
参考节奏曲线                 写作时打开 source_book 报告页浮层，
                           前端双图对比（拆书曲线 vs 当前作品已分析章节曲线）
桥段/爽点模式库              用户在拆书报告中将某章"收藏为桥段模板"
                           → 存入 material(type=BRIDGE_TEMPLATE, ref_analysis_chapter_id)
                           → 编辑器 AI 续写时可选注入 prompt
节奏体检                     对当前 novel 跑轻量版分析(仅摘要+tension)，
                           与目标 source_book 曲线做相似度提示
```

## 8. 安全设计

1. **鉴权**：JWT（Access 2h + Refresh 14d，Refresh 轮换），密码 BCrypt，登录失败 5 次锁定 10 分钟。
2. **数据隔离**：所有 novel/source 查询强制带 `user_id` 条件（MyBatis-Plus 拦截器自动注入，防越权）。
3. **上传安全**：扩展名白名单 + 魔数校验 + 50MB 限制 + zip 炸弹防护（EPUB/DOCX 解压比 >50 倍拒绝）+ 解析在 worker 容器（非 API 容器）执行。
4. **自定义正则防护**：用户自定义分章规则在沙箱线程执行，超时 5s 强杀；拒绝嵌套量词 `{n}{m}` 深度 >3 的 pattern。
5. **XSS/CSRF**：前端富文本走 ProseMirror 白名单序列化；Cookie 携带 SameSite=Lax；所有写接口校验来源。
6. **版权**：用户协议明示"上传内容仅限个人学习分析"；拆书原书不进入任何分享/协作功能（本期无协作，天然隔离）；导出文件加水印（用户名+时间）。

## 9. 非功能性设计

### 9.1 性能预算

| 指标 | 设计保证 |
|---|---|
| 百万字解析 ≤ 5 分钟 | 流式读取 + 批量入库（不含 AI）；AI 分析走异步任务不占此时限 |
| 编辑器输入无卡顿 | ProseMirror 单章 ≤ 5 万字流畅；打开大章分页加载（按段落虚拟滚动） |
| 打开章节首屏 < 500ms | 正文单表单查 + gzip 传输 |
| 任务抢占延迟 < 5s | worker 每 2s 轮询 PENDING 任务表 |

### 9.2 AI 成本控制（账）

以 100 万字、500 章小说全量分析估算（DeepSeek 级定价）：
- 摘要+情绪：500 章 × 输入 4k tokens ≈ 200 万输入 + 25 万输出 ≈ **¥3~5/本**
- 人物确认（15% 章节）：≈ ¥0.8
- 报告汇总：≈ ¥0.3
- **合计约 ¥4~6/本**，配合结果缓存（重复分析零成本）与抽样模式（-65%）。平台默认日额度 ¥2/用户即可控。

### 9.3 可靠性

- MySQL 每日 `mysqldump` + binlog 增量备份，保留 14 天，异地拷贝；
- MinIO 启用版本控制；
- 任务失败告警：DEAD 任务 > 3 个或 provider 熔断 > 10 分钟 → 通知管理员（邮件/Webhook）。

### 9.4 可观测

- 日志：logback JSON 格式 → 文件（容器环境接 Loki/ELK 可选）；
- 指标：Micrometer 暴露 `/actuator/prometheus`——任务队列深度、AI 调用量/延迟/成本、解析耗时；
- 链路：关键任务打 taskId 贯穿日志。

### 9.5 测试策略

- 解析层：构造 20 种章节格式样本（含异常：无章节、乱码、超大章）作为黄金测试集；
- AI 层：Prompt 模板版本化 + 录制回放测试（录制真实响应，CI 中断网可跑）；
- 并发：CAS 冲突、任务抢占的并发单元测试（多线程跑 100 次断言无丢失更新）。
